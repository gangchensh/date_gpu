## 0. Abstract

The Ventus multiplier wrapper (ArrayMultiplier) collapses three "take the
high 32 bits" operations into two at the result-selection point:
`res = Mux(isMAC(func), mac_out, Mux(func===FN_MULH | func===FN_MULHU,
result(63,32), result(31,0)))` (Multiplier.scala:204-205) — **FN_MULHSU(23)
is omitted**, so MULHSU falls into the low-half branch and returns the **low**
32 bits of the 64-bit product instead of the high 32 bits.

Ironically, the other half of the datapath is correct: operand formation
(:178-179) correctly selects sext(a)×zext(b) for MULHSU, and the
commented-out mulInputFuncTable (:161-177) proves the designer fully
understood MULHSU's semantics — **the input side remembers, the output side
forgets**; a one-line Boolean condition omission breaks the semantics of an
entire instruction.

The evidence chain is a complete closed loop: Lean machine proofs
(selection-function level → wrapper-level symbolic theorem → numerical
witness, three layers progressively amplified) + ChiselSim module-level
reproduction (MULHSU(0xFFFFFFFF,0xFFFFFFFF) measured 0x00000001, should be
0xFFFFFFFF, bit-exact agreement with the Lean witness) + Verilator
whole-machine reproduction + a one-line patch (adding FN_MULHSU to the
high-half condition) verified green in two regression rounds on the 35- and
38-patch trees.

## 1. Module function and design intent

### 1.1 Background concepts

- **RISC-V M-extension multiply family**: on a 32-bit architecture the 64-bit
  product is split across two instructions — MUL takes the low 32 bits; the
  high 32 bits come in three signedness variants: MULH (signed×signed), MULHU
  (unsigned×unsigned), **MULHSU (signed×unsigned)**. MULHSU is common in
  multi-precision arithmetic (generated by compilers for bignum
  multiplication). Ventus additionally defines custom vector versions
  VMULHSU_VV/VX.
- **Booth-2 (radix-4) multiplier**: this module's multiplication core is a
  XiangShan-lineage Booth-2 partial-product generator plus a CSA
  (carry-save adder) compression tree: multiplier a is cut into a 3-bit
  window every 2 bits, each window selects one of 0/±b/±2b as a partial
  product, 17 rows of partial products are compressed by the CSA tree into
  two rows (sum/carry), and a final addition yields the 66-bit product.
- **ArrayMultiplier wrapper**: the "shell" around the multiplication core —
  it decides per opcode whether each operand is sign-extended or
  zero-extended to 33 bits (:178-179), handles the addend for MACC-family
  operations (:200), and **selects the high or low 32 bits out of the 66-bit
  result per opcode** (:204-205, the site of this entry). latency=2,
  two-stage pipeline.

### 1.2 Design intent

The correct semantics of MULHSU: treat a as **signed**, b as **unsigned**,
and take the **high** 32 bits of the 64-bit product. For the hardware to
satisfy this, two places must cooperate: the operand-formation side
sext(a)/zext(b) (:178-179, correctly implemented), and the result-selection
side taking the high-half branch (:204-205, omitted).

## 2. Construct-by-construct reading of the original code

**Construct 1: operand formation — correct** (`Multiplier.scala:178-179`):

```scala
mulDataModule.io.a := Mux(io.in.bits.ctrl.alu_fn(4,0)===FN_MULH |
  io.in.bits.ctrl.alu_fn(4,0)===FN_MULHSU, signext(mul_in1), zeroext(mul_in1))
mulDataModule.io.b := Mux(io.in.bits.ctrl.alu_fn(4,0)===FN_MULH,
  signext(mul_in2), zeroext(mul_in2))
```

For MULHSU, a is sign-extended and b is zero-extended — correct.

**Construct 2: the commented-out mulInputFuncTable — record of design intent** (`:161-177`):

```scala
/*
val mulInputFuncTable = List(
  FN_MUL -> (zeroext, zeroext),
  FN_MULH-> (signext, signext),
  FN_MULHSU -> (signext, zeroext),   // ← the designer clearly knew MULHSU's extension rule
  FN_MULHU -> (zeroext, zeroext),
)
... LookupTree version of operand selection ...
*/
```

The table was commented out in favor of a hand-written Mux (construct 1), but
the extension rules are equivalent — proving that MULHSU was treated as a
first-class citizen throughout the refactoring.

**Construct 3: result high/low selection — ★defect site** (`Multiplier.scala:204-205`):

```scala
val xlen = len - 1
val res = Mux(isMAC(func), mac_out(xlen,0),
  Mux(func===FN_MULH | func===FN_MULHU,          // ★ func===FN_MULHSU omitted
    result(2*len-1, len),                         //   high-32-bit branch
    result(xlen,0)))                              //   low-32-bit branch — MULHSU falls here
```

func is consumed aligned with the datapath after being pipelined two cycles
via ctrlVec (`func = ctrlVec.takeRight(2).head.alu_fn(4,0)` at :199-200; the
alignment correctness is pinned down by `mulPipe_two_cycles`, see §4), so the
selection condition itself is the only defect point.

**Downstream chain** (no compensation point): DecodeUnit.scala:223 (scalar
MULHSU) and :377-378 (VMULHSU_VV/VX) decode to alu_fn=FN_MULHSU →
issue.scala:110 routes out_MUL → execution.scala:72,188 instantiates
ArrayMultiplier → result is written back directly. There is no correction
logic anywhere along the chain.

## 3. Defect analysis

### 3.1 Precise description of the defect

**Trigger surface**: the scalar MULHSU instruction and the vector
VMULHSU_VV/VX instructions, for all input combinations.

**Numerical characterization**: the hardware returns
`(sext(a)·zext(b))(31,0)` (low 32 bits of the product); the correct value is
`(sext(a)·zext(b))(63,32)` (high 32 bits). The two generally differ — they
coincide only by accident when the product's high 32 bits happen to equal its
low 32 bits.

**Witness** (Lean machine proof + bit-exact agreement with both RTL channels):
a=b=0xFFFFFFFF. a as signed = −1, b as unsigned = 0xFFFFFFFF, 66-bit product
= 0x3FFFFFFFF00000001; high 32 bits = 0xFFFFFFFF (correct value), low 32 bits
= 0x00000001 (actual hardware output). The product value was cross-checked
against an independent Python replica (a third expectation source independent
of the model, guarding against "model and test sharing the same error").

### 3.2 Root cause

An enumeration omission in a single-line Boolean condition: the high-half
branch lists `FN_MULH | FN_MULHU` and omits `FN_MULHSU`. Three "take the high
half" operations share the same result-selection point, but the condition
lists only two. Constructs 1/2 show this is not a misunderstanding of MULHSU
semantics — rather, the result selection, an **independent second site**, was
not checked in sync during the refactoring (LookupTree → hand-written Mux) or
maintenance. This kind of "the same semantic decision scattered across two
places, only one fixed" defect is exactly the target of line-by-line
comparative review.

### 3.3 Impact and tolerability

- **Impact**: three live instructions silently return wrong data. Scalar
  MULHSU is a compliant RISC-V M-extension instruction (generated by
  compilers for multi-precision arithmetic); VMULHSU is a Ventus custom
  vector instruction. The failure mode is wholesale loss of the high half —
  not a boundary corner case, but wrong on nearly every execution. No trap,
  no assertion; extremely hard to locate from the software side.
- **Tolerability**: regular testing never exposed it, showing the upstream
  software stack (including existing test kernels) never exercises
  MULHSU/VMULHSU — a case of "landmine not stepped on", not "no landmine".
  Once the software stack uses multi-precision multiplication, errors are
  systemic. Rating: **High** (functional-correctness level; trigger surface
  is an entire instruction).

## 4. Lean formal evidence

The evidence chain is amplified through three layers (all machine-checked,
zero sorry; line numbers measured under `lean/Ventus/Arith/`):

**Selection-function level** (Multiplier.lean:1875, bv_decide):

- `mulRes_mulhsu`: for any 66-bit result, MULHSU's selection output = the low
  32 bits. Pins the source semantics of :204-205 directly into a theorem.

**Wrapper-level symbolic theorem** (Multiplier.lean:2007, fully proved for arbitrary a b c):

- `mul_mulhsu_diverges`: `mulWrapOut MULHSU a b c =
  ((sext₆₆ a)·(zext₆₆ b))(31,0)` — per the source semantics, MULHSU is
  identical to "the low 32 bits of the correct product". The proof goes
  through `mulPlacedSum_eq_of_corr0` (:1789) plus sext/zext mixing lemmas,
  where "the correction term is zero on reachable inputs" is supplied by
  `mul_sext33_corr0` (:1770)/`mul_zext33_corr0` (:1782) (this is exactly the
  contract face of I-20; see that entry's report).

**Numerical witness** (Multiplier.lean:2017):

- `mul_mulhsu_witness`: ∃ a b, source output ≠ correct high 32 bits — with
  a=b=0xFFFFFFFF the source outputs 0x00000001, correct value 0xFFFFFFFF.

**Supporting chain** (guaranteeing that the "correct product" in the witness
is not the model talking to itself):

- `mulPlacedSum_eq` (Multiplier.lean:1721, manual proof, axioms only
  [propext, Classical.choice, Quot.sound]): the weighted sum of Booth partial
  products = sext(a)·sext(b) − last-row correction term — anchors "product"
  to mathematical multiplication;
- `mcsaDataModule33_eq_placedSum'` (MultiplierCSA.lean:1406, axioms only the
  standard three): the circuit-layer CSA tree's output = the arithmetic-layer
  partial-product sum, fully proved for arbitrary signed inputs — the
  circuit-to-arithmetic bridge leaves no numerical-exhaustion residue;
- execution-level propagation: `exmMulLaneOut_mulhsu` (ExeMul.lean:545,
  arbitrary inputs) + `exmMulLaneOut_mulhsu_witness` (:553) + two
  native_decide traces `exmVMulExe_test_mulhsu_low32` (:753) and
  `exmV2_test_mulhsu_low32` (:1090) — on both execution paths vMULexe and
  vMULv2, MULHSU outputs the low 32 bits;
- control group: `mul_wrap_mulh` (:1988)/`mul_wrap_mulhu` (:1997) prove that
  MULH/MULHU take the high-half branch **correctly** — the defect is confined
  precisely to the single opcode MULHSU.

## 5. Simulation verification (dual-channel execution + patched-tree regression)

**ChiselSim module level** (`repro/ArrayMultiplierBugRepro.scala`, executed
2026-09-06/07, doc/22): MULHSU(0xFFFFFFFF, 0xFFFFFFFF) measured
**0x00000001** (should be 0xFFFFFFFF) — bit-exact agreement with the Lean
witness `mul_mulhsu_witness`; control group MULHU on the same operands =
0xFFFFFFFE passes (proving the high-half path itself works). Verdict:
**reproduction succeeded**.

**Verilator whole-machine level** (`repro/verilator/` kernel
`i15_mulhsu_low32`, executed 2026-09-07, doc/22): executing
`mulhsu(0xFFFFFFFF,0xFFFFFFFF)` in the whole-machine environment yields
**0x00000001** (low 32 bits); the correct value should be 0xFFFFFFFF.
Verdict: **reproduction succeeded** (one of the 8 reproduced among 9 target
bugs).

**Patched-tree regression** (the 35-patch tree of 2026-09-07 and the 38-patch
merged tree of 2026-09-10, doc/22): ArrayMultiplierBugRepro **2/2 green** —
after the fix MULHSU returns 0xFFFFFFFF, and the control group stays green.

## 6. Upstream impact analysis

- **Trigger surface**: at the decode layer, DecodeUnit.scala:223 (scalar
  MULHSU) and :377-378 (VMULHSU_VV/VX) are both live paths; the issue layer
  issue.scala:110 routes out_MUL; the execution layer instantiates at
  execution.scala:72,188. No downstream compensation point on the chain.
- **Why upstream never found it**: existing test kernels never generate
  MULHSU/VMULHSU (multi-precision arithmetic is rare in GPU kernels) — a test
  coverage blind spot.
- **Upstream corroboration**: the commented-out mulInputFuncTable at
  :161-177 explicitly lists FN_MULHSU → (signext, zeroext) — the designer
  knew the instruction; the omission happened at the independent
  result-selection site.
- **Same-family note**: I-20 (Booth last-row correction term) was swept in
  the same module and proved unreachable under the current configuration —
  MULHSU is the only live functional bug in this module.

## 7. Fix and fix verification

**Patch** (`i15-multiplier-mulhsu.patch` (internal fix manifest; not released), single line):

```scala
// Multiplier.scala:204-205, add FN_MULHSU to the high-half condition:
-    Mux(func===FN_MULH | func===FN_MULHU, result(2*len-1, len), result(xlen,0)))
+    Mux(func===FN_MULH | func===FN_MULHU | func===FN_MULHSU, result(2*len-1, len), result(xlen,0)))
```

**Three-part fix verification**:

- Effectiveness: Lean fixed version (`lean/VentusF/Arith.lean`) —
  `farith_mul_mulhsu_fixed` (:70, fixed-version MULHSU = spec high 32 bits,
  arbitrary inputs), `farith_i15_witness` (:79, the original witness turns
  green), `farith_mulhsu_divergence_gone` (:88, the original wrong behavior
  eliminated);
- Regression safety: `farith_mul_regr` (:96, for func ≠ MULHSU the fixed
  version is bitwise equivalent to the original, including per-opcode
  instances such as `farith_mul_regr_mul/mulh/mulhu/macc`);
- RTL level: two rounds of ChiselSim regression on the 35-patch tree and the
  38-patch merged tree both 2/2 green (doc/22).

I-15 is a textbook single-line defect of the "same semantic decision
scattered across two places, only one fixed" kind: the operand-formation side
is completely correct for MULHSU, while the result-selection side omitted one
opcode, silently corrupting data for the entire MULHSU instruction family.
Its value lies in the textbook shape of the evidence chain — the Lean witness

the fix verification stands on both legs of machine-checked proof
(fixed-version theorems + regression equivalence) and measurement
